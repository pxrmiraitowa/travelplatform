# Travel Platform Module Builder

在这个旅游平台项目中新增功能模块时，按以下流程执行。

## 基本原则

- 优先复用现有代码结构、命名方式和页面模式，不先发明新规范。
- 保持后端分层清晰：`controller`、`service`、`mapper`、`entity`、`dto`、`vo`。
- 保持前端分层清晰：`api`、`views`、`components`、`router`、必要的状态管理。
- 统一使用现有 `Result` 返回格式。
- 不修改无关模块，不为了一个新功能重构整站。
- 以“业务链路完整、演示稳定、结构清晰”为优先目标。
- 不主动引入真实支付、复杂外部依赖或高风险第三方在线能力。
- 如果用户要求先设计再开发，必须先输出设计方案，待确认后再编码。
- 如果用户明确要求不要改代码，只输出方案、草稿、审查意见或测试建议。

## 第一步：先理解当前项目

开始实现前，先检查以下内容：

- 后端目录结构与包分层
- 前端页面目录、路由结构、布局组件
- 用户系统、订单系统、后台系统的已有做法
- 是否已有相似模块可复用
- 是否已有图片上传、内容管理、状态流转等能力
- 是否已有单元测试、集成测试、测试基类和测试数据脚本
- 数据初始化和本地运行方式

如果已有类似功能，优先沿用已有模式，而不是另起一套。

## 第二步：先输出模块设计

当用户提出“新增某个功能模块”时，先输出以下内容：

1. 数据结构设计
2. 与用户、订单、后台等现有模块的关联方式
3. 后端接口设计
4. 前端页面设计
5. 修改文件列表

如果模块涉及上传、订单状态、管理员处理、AI能力、评价、收藏、提醒等内容，也要在设计里单独说明边界和约束。

未获确认前，不默认直接编码；除非用户明确要求直接落地实现。

## 第三步：先划清模块边界

在设计阶段先明确：

- 这个模块负责什么
- 这个模块不负责什么
- 它是前台模块、后台模块，还是前后台联动模块
- 它是否依赖登录
- 它是否依赖订单状态
- 它是否需要图片上传
- 它是否需要管理员查看、删除、下架或处理
- 它是否涉及用户生成内容
- 它是否需要和 AI、规则计算或本地兜底逻辑联动

如果两个概念职责不同，优先拆开建模，不混在一张表或一个对象里。

## 第四步：数据建模规则

设计数据库表时遵循以下规则：

- 一张表只负责一个核心业务对象
- 明确每个字段的业务含义
- 关联字段即使不做数据库外键，也要说明语义
- 常规包含基础时间字段，如 `create_time`、`update_time`
- 只有确实存在业务状态时，才增加状态字段
- 不把内容表、订单表、评价表、上传资源表混在一起

新增模块时优先考虑是否需要以下独立模型：

- 主业务表
- 图片表或附件表
- 评价表
- 明细表
- 关联关系表
- 后台处理记录表

如果模块与用户、订单、管理员有关，要明确：

- 是实时关联读取，还是保存快照信息
- 展示时需要哪些用户字段
- 是否允许后续编辑影响历史数据展示

## 第五步：先判断与现有系统的关系

新增模块时，优先判断它与以下系统的关系：

### 用户系统

- 是否必须登录才能使用
- 数据是否归属于当前登录用户
- 页面展示是否要显示昵称、头像、手机号等信息
- 这些信息是实时读取还是写入快照

### 订单系统

- 是否必须基于订单触发
- 是否只能对已完成订单操作
- 是否允许重复提交
- 是否要在订单详情页增加入口
- 是否要在订单列表体现状态变化

### 后台系统

- 是否要提供管理员查看入口
- 是否支持删除、隐藏、驳回、修改状态
- 是否要放到后台内容管理、商品管理或订单管理下
- 是否需要额外权限判断

### 上传系统

- 是否需要图片、本地文件或附件上传
- 文件保存到哪里
- 数据库存什么字段
- 前端展示访问路径是什么
- 静态资源映射是否需要新增配置

### AI 或规则能力

- 是否依赖本地规则生成
- 是否需要第三方接口
- 第三方调用失败时是否有本地兜底
- 配置是否通过环境变量读取
- 是否影响演示稳定性

## 第六步：后端实现顺序

后端按以下顺序实现：

1. `entity`
2. `mapper`
3. `dto`
4. `vo`
5. `service`
6. `serviceImpl`
7. `controller`
8. 如需要，再补 `admin controller`
9. 更新 `schema.sql` 或相关初始化脚本
10. 如涉及上传、静态资源、拦截规则，再补配置类

实现时注意：

- 复用现有实体字段风格
- 复用已有分页、查询、详情接口模式
- 统一响应结构
- 不为了小模块引入新的复杂框架
- 对于非显然业务逻辑，补少量清晰注释

如果功能依赖订单状态或权限边界，要把校验逻辑放在服务层，而不是只依赖前端限制。

如模块包含明显业务规则、权限判断或订单状态约束，应同步补充对应测试，而不是只依赖手工联调。

## 第七步：前端实现顺序

前端按以下顺序实现：

1. `api` 接口封装
2. 路由注册
3. 列表页
4. 详情页
5. 创建页或编辑页
6. 复用组件或弹窗组件
7. 如有后台管理，再补后台页面
8. 如有明显入口，再补导航、按钮或跳转入口

实现时注意：

- 复用现有布局组件
- 页面命名、目录命名与现有模块一致
- 优先保持演示路径清晰
- 重要入口不要藏得太深
- 如果是后台页，优先沿用现有表格 CRUD 风格
- 如果是前台内容页，优先考虑列表、详情、发布三件套
- 如果是订单后置能力，优先挂到订单列表或订单详情页

## 第八步：针对典型模块类型的处理方式

### 内容型模块

例如分享、游记、评价、问答、评论：

- 登录后创建，公开浏览或按规则可见
- 与用户关联清晰
- 如果带图片，主表和图片表分开
- 后台通常提供查看和删除能力
- 视情况防止重复提交或越权删除

### 商品或资源型模块

例如酒店、房型、旅游产品、景点扩展：

- 前台关注展示、筛选、详情
- 后台关注 CRUD、上下架、图片管理
- 如有多图，区分封面图与图集
- 注意与订单或下单入口的衔接

### 订单后置型模块

例如评价、售后申请、出行反馈：

- 明确触发条件，一般要求订单状态满足前置条件
- 明确一单是否只能提交一次
- 入口一般挂在订单详情或订单列表
- 后台通常需要查看和管理

### 上传型模块

- 先用本地存储
- 明确物理路径和访问路径
- 数据库存储相对访问路径或统一可访问地址
- 确保静态资源映射正确
- 限制文件大小和类型
- 避免上传逻辑影响已有模块

### AI 增强型模块

- 先保证没有第三方时也能演示
- 提供本地规则兜底
- 第三方配置走环境变量
- 不把真实密钥写入仓库
- 输出结果尽量结构化，方便前端展示和保存

## 第九步：权限与越权检查

实现完成后，至少检查以下权限问题：

- 未登录用户是否能访问本应登录后才能使用的接口
- 普通用户是否能操作别人的数据
- 普通用户是否能访问管理员接口
- 是否能伪造 ID 读取不属于自己的详情数据
- 是否能重复提交本应唯一的业务数据
- 上传接口是否缺少鉴权
- 删除、修改、状态变更是否只靠前端控制而后端未校验

任何涉及“当前用户”和“当前订单”的能力，都必须在后端再次校验归属关系。

## 第九点五步：测试补充要求

新增模块时，测试作为补充要求加入，不要求为测试重构无关模块，但不能完全跳过验证。

优先沿用项目现有测试风格：

- DTO 或请求对象校验，优先补参数校验测试
- 服务层核心业务规则，优先补单元测试
- 关键业务链路，优先补集成测试
- 能复用现有测试基类、测试工具和测试数据时，不重复造轮子

### 单元测试要求

优先为以下内容补单元测试：

- 业务前置条件
- 状态流转限制
- 当前用户归属校验
- 重复提交限制
- 关键字段清洗或格式处理
- 异常分支与业务异常抛出

单元测试优先贴近当前项目已有写法，使用现有的 `JUnit 5`、`Mockito`、`AssertJ` 风格，重点覆盖服务层逻辑，而不是只测简单 getter/setter。

如果模块包含请求对象校验规则，补充类似现有 DTO 校验测试的用例，覆盖合法值与非法值。

### 集成测试要求

当模块满足以下任一情况时，优先补集成测试：

- 涉及登录态或权限判断
- 涉及订单创建、状态变更、评价、取消等完整流程
- 涉及前后台联动
- 涉及分享、评价、后台删除等跨模块链路
- 涉及上传、静态资源访问路径或测试环境隔离

集成测试优先复用项目现有的 `SpringBootTest + MockMvc` 方案，以及统一测试基类中的能力，例如：

- 登录并获取 token
- 创建测试用户或管理员
- 构造联系人、订单、内容数据
- 统一发起 JSON 请求
- 统一断言 `Result` 返回结构
- 在测试前清理测试数据并恢复受影响库存

### 测试环境要求

如需新增集成测试，遵循项目现有测试环境约定：

- 使用 `test` profile
- 复用独立测试数据库配置
- 复用测试 SQL 初始化数据
- 上传相关测试不要污染正式上传目录
- 测试数据命名尽量带明显测试标记，便于清理和排查

### 测试范围控制

这是课程项目，测试目标是保障核心链路稳定，不追求高覆盖率数字。

优先保证以下内容被验证：

- 核心成功路径
- 关键失败路径
- 权限边界
- 与订单、用户、后台的联动逻辑
- 影响演示稳定性的关键流程

如果某个模块很轻，只补必要单元测试或最小集成验证即可，不为了“看起来完整”而增加大量低价值测试。

## 第十步：联调与验证

完成开发后，至少验证以下内容：

- 后端能正常启动
- 数据库初始化或新增表逻辑正常
- 前端能正常运行或构建通过
- 关键页面能打开
- 核心链路可走通
- 与订单、用户、后台的关联逻辑符合预期
- 上传功能可正常展示
- 管理员查看或删除功能可用
- 权限控制基本正确
- 新增或受影响的核心业务规则已有对应单元测试或集成测试验证
- 如项目已有现成测试基类或测试数据脚本，优先复用并保证测试可重复执行

如果出现问题，优先排查真实根因，不只处理表面报错。

## 第十一步：最终输出格式

完成后，输出以下内容：

- 本次实现了什么
- 图片上传说明（如涉及）
- 测试步骤
- 数据安全或越权风险提示
- 已知限制或后续可优化点

如果用户只要设计稿，不输出代码说明，改为输出：

- 设计结论
- 推荐实现顺序
- 风险点
- 预计修改位置

## 课程项目特别要求

这是课程项目，优先满足以下目标：

- 功能链路完整
- 本地可跑通
- 演示稳定
- 代码结构清晰
- 与现有模块风格统一

避免为“看起来高级”而引入不必要复杂度。优先做出稳定、可讲解、可演示、可验收的实现。
