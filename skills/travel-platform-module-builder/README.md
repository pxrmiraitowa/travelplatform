# travel-platform-module-builder

## 1. 背景说明

本目录中的 skill 不是通用代码模板，而是我们在本课程项目开发过程中，结合多个功能模块的实际实现过程，总结出的一个 AI 使用规则集。

本项目是一个基于 Spring Boot + Vue 3 的综合旅游平台课程项目。在开发过程中，我们陆续完成了前台业务模块、后台管理模块、订单相关能力、图片上传能力、内容分享与评价能力、AI 行程规划能力等功能扩展。  
在多轮与 AI 协作后，我们将“如何让 AI 更规范地参与项目开发”整理成了这个 skill。

这个 skill 的目的不是替代人工设计，而是让 AI 在参与课程项目开发时，能够更稳定地遵守项目结构、业务边界和实现流程。

## 2. skill 的作用

`travel-platform-module-builder` 用于指导 AI 在现有旅游平台项目中新增业务模块或扩展已有模块。

它的核心作用包括：

- 先阅读现有项目结构，而不是脱离上下文直接生成代码
- 先输出设计方案，再进入编码阶段
- 明确模块与用户系统、订单系统、后台系统、上传系统、AI 功能之间的关联关系
- 要求 AI 按现有项目的前后端结构完成实现
- 在实现后补充测试、联调、越权风险和交付说明

换句话说，这个 skill 体现的是“如何管理 AI 的工作流程”，而不是只让 AI 输出一段代码。

## 3. 这个 skill 体现的 AI 使用能力

我们认为，这个 skill 主要体现了以下几类 AI 使用能力：

### 3.1 将模糊需求结构化

课程项目中的需求通常不是完整技术规格，而是业务描述。  
在这种情况下，我们要求 AI 先把需求整理为：

1. 数据结构设计
2. 模块关联方式
3. 后端接口设计
4. 前端页面设计
5. 修改文件列表

这样可以避免 AI 直接编码时偏离需求。

### 3.2 让 AI 遵守现有项目架构

我们没有让 AI 自由发挥，而是明确要求它遵循本项目已有的技术栈和层次结构，例如：

- 后端使用 `controller / service / mapper / entity / dto / vo`
- 前端使用 `api / views / components / router`
- 接口返回统一使用 `Result`
- 不修改无关模块
- 优先复用现有代码模式

这体现的是“约束 AI 输出”的能力。

### 3.3 让 AI 理解业务边界

在本项目中，不同模块之间存在明显业务关系，例如：

- 用户与内容发布
- 订单与评价
- 后台与内容管理
- 图片上传与静态资源访问
- AI 行程规划与本地兜底逻辑

这个 skill 会要求 AI 在实现前先判断这些关系，而不是把所有功能混在一起处理。

### 3.4 让 AI 补充测试与风险意识

我们不仅要求 AI 写功能，还要求它关注：

- 单元测试与集成测试补充
- 订单状态前置条件
- 数据归属校验
- 后台权限边界
- 上传访问路径正确性
- 最终测试步骤与风险提示

这体现的是“把 AI 用在完整开发流程中”，而不只是写代码片段。

## 4. 这个 skill 的来源

这份 skill 不是凭空写出来的，而是从本项目多个实际功能扩展过程中总结而来。  
它综合参考了我们在项目中已经完成或扩展过的这类模块能力：

- 分享与评价模块
- 图片上传与展示能力
- 订单列表、详情与状态流转相关能力
- 后台内容管理能力
- 行程规划与 AI 规划能力
- 用户资料、联系人、内容归属等相关能力

因此，它更像是本项目开发方法的总结，而不是通用模板。

```

```

```text
$travel-platform-module-builder 给订单系统增加售后申请功能，并按照现有代码风格实现。
```

## 6. skill 的核心特点

这份 skill 的设计重点不是“让 AI 更自由”，而是“让 AI 更可控”。  
它强调以下特征：

- 先分析，再实现
- 先设计，再编码
- 先明确边界，再处理关联
- 尽量复用，而不是重复发明
- 功能完成后补充测试、联调与风险说明

对于课程项目来说，这种方式更有利于：

- 保持代码结构稳定
- 减少无关改动
- 提高功能演示的完整性
- 体现团队对 AI 的有效使用能力

## 8. 总结

这份 skill 反映的不是“我们会不会让 AI 生成代码”，而是“我们能不能把 AI 纳入一个受控的开发流程”。

在本课程项目中，我们尝试将多轮 AI 协作经验沉淀成可复用规则，使 AI 不只是回答问题，而是按照项目上下文、模块边界、实现顺序和验证要求参与开发。  
这也是我们认为更有价值的 AI 使用方式。
