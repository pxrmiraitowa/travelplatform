# 角色D微服务拆分双人协作计划

## 1. 目标与范围

本计划用于两人协作完成旅游平台的微服务拆分工作。目标是在不破坏原单体项目演示能力的前提下，逐步形成可独立启动、可独立开发、可独立测试的微服务工程。

当前微服务骨架位于：

```text
travel-platform-microservices/
```

已规划服务包括：

| 服务模块 | 端口 | 主要职责 |
| --- | ---: | --- |
| `common-lib` | - | 通用返回结果、异常、常量、基础 VO |
| `user-service` | 8101 | 用户、登录认证、个人资料、后台用户管理 |
| `product-service` | 8102 | 旅游产品、线路、酒店、门票、库存、价格查询 |
| `order-service` | 8103 | 下单、订单状态、模拟支付、退款、售后 |
| `content-trip-service` | 8104 | 攻略、游记、评论、收藏、行程、推荐展示数据 |

## 2. 协作原则

1. 原单体项目先保持可运行，不在拆分初期直接删除原功能代码。
2. 两人开发尽量按服务边界分离，避免同时修改同一批文件。
3. 公共代码先进入 `common-lib`，业务服务只依赖公共模块，不反向依赖。
4. 每次迁移一个完整闭环：Controller、Service、Mapper、Entity、DTO、VO、配置、接口验证一起完成。
5. 不接入真实支付和第三方在线 API，涉及支付、短信、地图等能力统一使用模拟实现。
6. 每个阶段都要能本地编译，至少保证健康检查接口可访问。

## 3. 人员分工

### 成员 A：基础设施与用户/订单方向

成员 A 负责偏平台底座和交易链路的部分：

| 工作包 | 具体内容 | 主要目录 |
| --- | --- | --- |
| 公共模块维护 | `Result`、异常、通用常量、跨服务 DTO、基础工具类 | `common-lib` |
| 用户服务迁移 | 登录、注册、用户信息、用户状态、后台用户管理 | `user-service` |
| 订单服务迁移 | 订单创建、订单查询、状态流转、模拟支付、退款 | `order-service` |
| 认证链路处理 | JWT 校验、用户上下文传递、接口权限边界 | `common-lib`、`user-service`、`order-service` |
| 订单调用适配 | 订单服务调用用户和产品数据时的本地模拟/Feign 预留接口 | `order-service` |

### 成员 B：产品与内容/行程方向

成员 B 负责偏资源展示和内容链路的部分：

| 工作包 | 具体内容 | 主要目录 |
| --- | --- | --- |
| 产品服务迁移 | 线路、酒店、门票、景点、库存、价格、搜索筛选 | `product-service` |
| 内容行程服务迁移 | 攻略、游记、评论、收藏、行程规划、推荐数据 | `content-trip-service` |
| 前台查询接口适配 | 产品详情、列表、内容详情、评论列表等读接口 | `product-service`、`content-trip-service` |
| 数据归属校验 | 按数据表归属表确认表和实体归属，不跨服务直接操作表 | `docs/数据表归属表.md` |
| 展示链路联调 | 首页、详情页、内容页所需接口返回结构稳定 | `product-service`、`content-trip-service` |

## 4. 可并行工作拆分

### 阶段一：工程骨架与公共规范

| 任务 | 负责人 | 是否可并行 | 交付物 |
| --- | --- | --- | --- |
| 创建 Maven 多模块工程 | A | 否 | `travel-platform-microservices/pom.xml` |
| 创建四个服务启动类和端口配置 | A | 是 | 各服务 `Application` 与 `application.yml` |
| 整理 `common-lib` 通用返回、异常、常量 | A | 是 | `common-lib` 基础类 |
| 阅读并确认服务划分、接口清单、数据表归属 | B | 是 | 问题清单或确认记录 |
| 编写两人协作计划和 README | A | 是 | 本文档、微服务 README |

验收标准：

1. 四个服务模块能够编译。
2. 每个服务都有 `/api/public/health` 和 `/api/public/version`。
3. 文档明确服务边界和后续迁移顺序。

### 阶段二：用户服务与产品服务并行迁移

| 任务 | 负责人 | 是否可并行 | 依赖 |
| --- | --- | --- | --- |
| 迁移用户实体、DTO、VO、Mapper | A | 是 | `common-lib` 已稳定 |
| 迁移登录、注册、用户资料接口 | A | 是 | 用户表结构确认 |
| 迁移产品实体、DTO、VO、Mapper | B | 是 | 数据表归属已确认 |
| 迁移产品列表、详情、筛选接口 | B | 是 | 产品表结构确认 |
| 补充接口返回示例 | A/B | 是 | 对应接口完成 |

验收标准：

1. `user-service` 能完成登录/注册/用户信息查询的基本演示。
2. `product-service` 能完成产品列表、详情、搜索筛选的基本演示。
3. 用户服务不直接访问产品表，产品服务不直接访问用户表。

### 阶段三：订单服务与内容行程服务并行迁移

| 任务 | 负责人 | 是否可并行 | 依赖 |
| --- | --- | --- | --- |
| 迁移订单实体、DTO、VO、Mapper | A | 是 | 用户、产品核心读接口稳定 |
| 迁移订单创建、查询、取消接口 | A | 是 | 产品价格/库存查询方式确定 |
| 实现模拟支付和订单状态流转 | A | 是 | 订单基础接口完成 |
| 迁移攻略、游记、评论、收藏接口 | B | 是 | 用户身份传递方式确定 |
| 迁移行程规划和推荐展示接口 | B | 是 | 产品基础数据可查询 |

验收标准：

1. `order-service` 能完成“选择产品 -> 创建订单 -> 模拟支付 -> 查看订单”的闭环。
2. `content-trip-service` 能完成内容浏览、评论、收藏、行程展示的闭环。
3. 跨服务数据读取优先通过接口或临时适配层，不直接跨库跨表访问。

### 阶段四：联调、网关预留与演示稳定

| 任务 | 负责人 | 是否可并行 | 交付物 |
| --- | --- | --- | --- |
| 梳理前端接口地址切换方式 | A/B | 是 | 环境变量或代理配置说明 |
| 增加跨服务调用适配说明 | A | 是 | 调用链说明和失败降级策略 |
| 完成核心业务流联调 | A/B | 否 | 演示流程清单 |
| 补充 Postman/接口测试记录 | A/B | 是 | 接口验证记录 |
| 整理最终答辩说明 | A/B | 是 | 微服务拆分成果说明 |

验收标准：

1. 本地可以同时启动多个服务。
2. 核心业务流程可演示。
3. 出现某个非核心服务不可用时，系统有明确的演示降级方式。

## 5. 分支与提交策略

推荐使用当前分支作为微服务拆分主开发分支：

```text
codex/microservices-split
```

两人可以继续从该分支切出个人开发分支：

| 人员 | 建议分支 | 用途 |
| --- | --- | --- |
| 成员 A | `codex/microservices-a-user-order` | 公共模块、用户服务、订单服务 |
| 成员 B | `codex/microservices-b-product-content` | 产品服务、内容行程服务 |

合并节奏：

1. 阶段一完成后合并一次，形成稳定骨架。
2. 用户服务和产品服务各自完成后分别合并，先保证两个基础服务可运行。
3. 订单服务和内容行程服务完成后再合并。
4. 每次合并前先执行对应模块编译。

提交建议：

```text
docs: add two-person microservice collaboration plan
feat: add microservice project skeleton
feat(user): migrate user basic APIs
feat(product): migrate product query APIs
feat(order): migrate order flow APIs
feat(content): migrate content and trip APIs
```

## 6. 每日协作检查点

每天至少同步一次以下内容：

1. 今天改了哪些服务和接口。
2. 是否修改了 `common-lib`，是否会影响对方服务。
3. 是否新增或调整了 DTO/VO。
4. 是否有数据表归属冲突。
5. 是否有前端接口路径变化。
6. 当前服务是否能独立启动或至少编译通过。

## 7. 冲突处理规则

1. `common-lib` 的新增字段、常量、DTO 需要先口头确认，再提交。
2. 同一个接口返回结构只能由接口负责人修改，另一人通过适配层使用。
3. 数据表归属以 `docs/数据表归属表.md` 为准，发现不合理时先改文档再改代码。
4. 原单体代码作为参照来源，不在迁移未完成前大规模删除。
5. 合并冲突优先保留已经编译通过的一方，再补齐另一方业务。

## 8. 当前下一步执行建议

当前已经完成微服务基础骨架，下一步建议按下面顺序推进：

1. 成员 A 提交并推送当前骨架。
2. 成员 A 开始迁移 `common-lib` 中原项目已有的 `Result`、异常和登录相关公共类。
3. 成员 B 同时整理产品、内容、行程相关 Controller 与表结构对应关系。
4. 成员 A 完成 `user-service` 登录/注册最小闭环。
5. 成员 B 完成 `product-service` 产品列表/详情最小闭环。
6. 双方进行第一次联调，确认用户身份、产品查询、接口返回格式一致。
