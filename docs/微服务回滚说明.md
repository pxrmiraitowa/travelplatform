# 微服务 Kubernetes 回滚说明

## 1. 目标

当新版本部署后出现功能、健康检查或业务回归异常时，将一个服务、一组业务服务或全部服务恢复到 Kubernetes 中保存的历史版本，并在回滚后重新执行健康检查。

回滚只修改 Deployment，不回滚 MySQL 数据。涉及数据库结构变化的版本必须额外准备向前兼容的迁移方案或单独的数据恢复脚本。

## 2. 支持范围

| 目标 | 包含的 Deployment |
| --- | --- |
| `all` | 4 个业务服务、网关和前端 |
| `business` | `user-service`、`product-service`、`order-service`、`content-trip-service` |
| 单服务 | 上述任一服务、`gateway-service` 或 `frontend` |

## 3. 使用方法

```bash
# 全部服务回滚到各自的上一版本
bash scripts/rollback-kind.sh all

# 只回滚四个业务服务
bash scripts/rollback-kind.sh business

# 只回滚网关
bash scripts/rollback-kind.sh gateway-service

# 将订单服务回滚到指定的 Kubernetes revision
bash scripts/rollback-kind.sh order-service 3
```

指定 revision 时只能选择一个 Deployment，因为每个 Deployment 独立维护版本号，不能把同一个 revision 安全地套用到所有服务。

## 4. 基本流程

1. 检查 Kubernetes 命名空间和目标 Deployment 是否存在。
2. 保存每个目标的回滚前历史。
3. 回滚到上一版本或指定 revision。
4. 等待每个 Deployment 完成 rollout。
5. 记录回滚前后镜像和版本历史。
6. 执行全部微服务、网关、前端和数据库健康检查。
7. 将证据保存到 `artifacts/rollback/`。

脚本在执行任何变更前会预检查所有目标。执行 `all` 或 `business` 时，只要一个服务没有可回滚版本，就会在修改集群前停止，避免只回滚一部分服务。

## 5. 流水线演练

在 GitHub Actions 手动运行流水线时，可勾选 `run_rollback_drill`。流水线会：

1. 为 `gateway-service` 创建一个不改变业务行为的新 revision。
2. 确认新 revision 已成功部署。
3. 调用回滚脚本恢复上一 revision。
4. 验证临时标记已经消失。
5. 再次执行健康检查并保留回滚证据。

该演练验证的是 Kubernetes 版本回滚机制，不会回滚数据库，也不会发布虚假的测试结果。

## 6. 现场检查说明

```bash
kubectl -n travel-platform rollout history deployment/gateway-service
kubectl -n travel-platform get deployments
kubectl -n travel-platform get pods
```

检查时重点说明：每个微服务独立维护镜像和 revision；可以单服务回滚，避免无关服务同时受影响；全量回滚前会统一预检查；回滚完成后必须通过健康检查才能判定成功。
