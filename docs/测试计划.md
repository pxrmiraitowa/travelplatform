# 出行旅游平台测试计划

## 1. 文档信息

| 项目 | 内容 |
| --- | --- |
| 项目名称 | 出行旅游平台 |
| 测试对象 | Spring Boot 单体兼容版本、微服务后端、Vue 前端、MySQL、Docker 与 Kubernetes 部署配置 |
| 目标分支 | GitHub `codex/microservices-ci-integration`，合并目标为 `dev` |
| 计划版本 | V1.0 |
| 编制日期 | 2026-08-29 |
| 测试负责人 | 项目测试小组 |

## 2. 测试目标

本轮测试用于验证出行旅游平台主要业务功能、业务规则、异常分支、模块协作、数据库访问、接口调用和页面入口是否符合需求，并验证自动化测试能否作为持续集成流水线的质量门禁。

具体目标如下：

1. 关键类、关键方法和核心业务规则具备有效单元测试。
2. 单元测试必须包含明确断言，不能只以“程序未报错”作为通过依据。
3. 集成/API 测试覆盖模块调用、数据库读写、认证授权和主要接口。
4. 每个核心业务用例应覆盖主成功流程、重要备选流程和异常流程。
5. 端到端测试应从页面或接口入口完成一条完整业务链路，并逐步覆盖业务用例清单。
6. 任一强制测试阶段失败时，持续集成流水线必须停止，不得继续发布镜像或执行部署。
7. 测试报告必须记录测试总数、通过数、失败数、失败原因和运行环境。

## 3. 测试范围

### 3.1 后端单元测试

重点覆盖以下模块：

- 认证与用户：注册、登录、用户资料、常用联系人、JWT。
- 商品与查询：机票、火车票、酒店、旅游产品、价格比较。
- 交易：订单创建、库存扣减、优惠券、订单查询、取消与库存恢复。
- 内容与互动：评价、旅行分享、媒体上传。
- 行程：人工行程、AI 行程、本地降级和用户数据隔离。
- 后台管理：用户、商品、订单、内容和仪表盘。
- 通用能力：请求校验、全局异常处理和业务错误码。

主要代码目录：

```text
travel-platform-server/src/test/java/com/travelplatform/service
travel-platform-server/src/test/java/com/travelplatform/dto
travel-platform-server/src/test/java/com/travelplatform/security
travel-platform-server/src/test/java/com/travelplatform/common
```

### 3.2 后端集成/API 测试

重点覆盖：

- 注册、登录和令牌认证。
- 用户资料与常用联系人增删改查。
- 航班、火车票、酒店和旅游产品查询。
- 机票订单创建、列表、详情和取消。
- 火车票、酒店和旅游订单创建。
- 价格提醒创建、查询和删除。
- 评价、旅行分享和后台管理。
- 文件上传、库存扣减及取消后的库存恢复。
- 行程规划创建、修改、删除、AI 预览及越权访问拦截。

主要代码目录：

```text
travel-platform-server/src/test/java/com/travelplatform/integration
```

微服务单元测试位于：

```text
travel-platform-microservices/*-service/src/test/java
```

部署后的公开 API 与 14 个业务场景回归位于：

```text
travel-platform-web/regression/public-api.test.js
travel-platform-web/regression/business-e2e.test.js
```

### 3.3 前端单元测试

覆盖以下前端关键点：

- 登录接口调用和参数传递。
- 登录页面交互与关闭导航。
- 用户状态管理。
- 路由配置和导航行为。
- Axios 请求拦截和异常处理。
- 价格比较组件渲染与交互。

测试文件位于 `travel-platform-web/src` 下，以 `*.test.js` 命名。

### 3.4 端到端测试

端到端测试使用 Playwright。最低要求不是只检查页面文字，而是从用户入口完成完整业务流程。

计划优先覆盖：

1. 用户注册、登录、退出。
2. 查询航班、填写联系人、创建订单、查看订单详情、取消订单。
3. 查询酒店、选择房型、创建订单。
4. 创建行程、添加行程项、查看详情、删除行程。
5. 管理员登录、商品查询和订单状态处理。
6. 未登录访问、普通用户越权和非法输入等异常场景。

当前 E2E 目录：

```text
travel-platform-web/tests/e2e
```

## 4. 测试策略

| 测试层级 | 测试方法 | 有效性判断 |
| --- | --- | --- |
| 单元测试 | JUnit 5、Mockito、AssertJ、Vitest | 对返回值、业务错误码、状态变化和依赖调用进行明确断言 |
| 集成/API 测试 | Spring Boot Test、MockMvc、JdbcTemplate、真实 MySQL | 同时验证 HTTP 响应、业务响应码和数据库最终状态 |
| 端到端测试 | Playwright、Chromium | 从页面入口完成业务流程，并检查关键页面和业务结果 |
| 部署验证 | Docker Compose、Kind、Kubernetes、健康检查 | MySQL、4 个业务服务、网关和前端可部署，依赖顺序、网络和健康状态正确 |

## 6. 测试数据计划

固定测试数据位于：

```text
travel-platform-server/src/test/resources/sql/data-test.sql
```

数据类型包括角色、用户、航班、火车票、酒店、房型、旅游产品、优惠券和景点。

动态测试数据由集成测试公共基类创建：

```text
travel-platform-server/src/test/java/com/travelplatform/integration/AbstractIntegrationTest.java
```

动态用户采用 `iu` 和 `ia_` 前缀。每个测试开始前清理测试用户关联的订单、评价、分享、提醒、行程和联系人，并恢复库存。日期型数据必须相对于测试执行日期动态生成，避免固定日期过期导致测试失效。

## 7. 执行流程

### 7.1 环境准备

1. 拉取 GitHub `codex/microservices-ci-integration` 最新代码。
2. 启动独立 MySQL 测试数据库并初始化结构及测试数据。
3. 安装后端和前端依赖。
4. 确认测试配置没有指向生产环境。

### 7.2 后端测试

执行全部测试：

```powershell
cd travel-platform-server
mvn test
```

分层执行：

```powershell
mvn "-Dtest=!*IntegrationTest" test
mvn "-Dtest=*IntegrationTest" test
```

结果目录：

```text
travel-platform-server/target/surefire-reports
travel-platform-server/target/site/jacoco
```

### 7.3 前端单元测试

```powershell
cd travel-platform-web
npm ci
npm run test:unit -- --pool=threads --maxWorkers=1
```

### 7.4 端到端测试

启动前后端后执行：

```powershell
cd travel-platform-web
npm run test:e2e
```

结果包括控制台结果、JUnit XML、HTML 报告，以及失败时的截图和 Trace。

### 7.5 Docker 验证

```powershell
docker compose config --services
docker compose up -d --build
docker compose ps
```

验证 `mysql`、`user-service`、`product-service`、`order-service`、`content-trip-service`、`gateway-service` 和 `frontend` 均为运行或健康状态，并通过 `http://127.0.0.1:8088` 访问系统。

## 8. 准入与退出标准

### 8.1 准入标准

- 需求和业务用例清单已确认。
- 测试分支可构建。
- 测试数据库可用，测试数据可重复初始化。
- 强制测试命令和报告目录明确。

### 8.2 通过标准

- 单元测试失败数为 0、错误数为 0。
- 集成/API 测试失败数为 0、错误数为 0。
- 前端单元测试失败数为 0。
- 核心 E2E 业务流程全部通过。
- Docker Compose 至少定义并成功运行 3 个容器。
- 不存在阻断演示或发布的高优先级缺陷。

### 8.3 流水线门禁

以下任一情况发生时流水线必须停止：

- 编译或构建失败。
- 单元测试、集成测试、前端测试或 E2E 测试失败。
- 测试报告未生成。
- Docker 镜像构建失败。
- 容器健康检查失败。

只有所有强制测试通过后，才允许构建、推送镜像和执行部署。

## 9. 风险与应对

| 风险 | 影响 | 应对措施 |
| --- | --- | --- |
| 固定旅游日期过期 | 集成测试随时间失效 | 使用相对当前日期动态生成测试数据 |
| 本地 MySQL 数据残留 | 测试互相影响 | 测试前清理前缀数据并恢复库存 |
| 前端测试 worker 启动超时 | 测试文件无法执行 | CI 固定 Node 版本，本地必要时限制为单 worker |
| E2E 只验证页面文字 | 无法证明业务闭环 | 增加登录、查询、下单、取消等完整流程 |
| Docker 服务未实际启动 | 无法提供运行证据 | 检查前启动 Docker Desktop并保存 `docker compose ps` 结果 |
