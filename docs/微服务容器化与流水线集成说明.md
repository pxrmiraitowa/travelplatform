# 微服务容器化与流水线集成说明

## 1. 集成来源

本次集成参考新远程仓库 `https://github.com/pxrmiraitowa/travelplatform.git` 的 `dev` 分支，该分支已包含单体后端版本的 Docker Compose、Dockerfile、Nginx 配置和 GitHub Actions 流水线。

由于当前项目已经拆分为 `user-service`、`product-service`、`order-service`、`content-trip-service` 和 `gateway-service`，不能直接合并单体 `dev` 分支，否则会删除当前微服务目录并回退到单体后端。实际采用的策略是在当前微服务稳定分支上新建 `codex/microservices-ci-integration`，选择性迁移容器化和流水线设计。

## 2. 当前集成内容

| 内容 | 说明 |
| --- | --- |
| `.env.example` | 提供本地 Compose 端口、镜像标签、MySQL 密码和 JWT 密钥示例 |
| `docker-compose.yml` | 编排 MySQL、数据库初始化、五个微服务和前端 Nginx |
| `travel-platform-microservices/Dockerfile` | 通过 `SERVICE_NAME` 构建指定 Spring Boot 微服务镜像 |
| `travel-platform-microservices/.dockerignore` | 排除 `target`、日志、上传目录等无关构建上下文 |
| `travel-platform-microservices/scripts/init-local-databases.sh` | Linux/容器环境下初始化 `travel_user`、`travel_product`、`travel_order`、`travel_content_trip` |
| `travel-platform-web/Dockerfile` | 构建 Vue 前端并交给 Nginx 托管 |
| `travel-platform-web/nginx.conf` | 将 `/api/**` 代理到 `gateway-service:8000` |
| `.github/workflows/ci-cd.yml` | 执行编译、测试、镜像推送、Kind 部署、健康/版本检查、表归属检查和端到端回归 |

## 3. 本地容器启动方式

在项目根目录执行：

```powershell
docker compose up --build
```

默认前端入口为：

```text
http://localhost:8088
```

gateway 入口为：

```text
http://localhost:8000
```

如果本机已有 MySQL 占用 `3306`，Compose 默认将容器 MySQL 映射到宿主机 `3307`，不影响容器内部服务访问。

## 5. Kubernetes 与自动部署

多微服务 Kubernetes 版本已完成：五个后端分别拥有 Deployment/Service，前端通过 Nginx 访问 gateway，数据库由 StatefulSet 和一次性初始化 Job 提供。提交到 `dev` 或 `codex/**` 后，GitHub Actions 自动构建版本化镜像并推送 GHCR，再创建临时 Kind 集群完成真实部署。

部署门禁包括 Deployment rollout、每个服务的健康和版本接口、四库表归属、14 个业务场景回归。手动运行流水线时可开启部署失败演练，记录镜像拉取失败证据并自动恢复。

| 数据库隔离 | `scripts/verify-table-ownership.sh` | 四个数据库只允许出现归属表，越界即失败 |

本次复验时发现 `db-init` 首次启动会为获取 MySQL JDBC 驱动下载整个 `product-service` 离线依赖，耗时过长且日志不明显。现已改为只拉取 `mysql-connector-j`，并输出下载、编译、初始化三个阶段日志，方便后续现场说明和失败定位。

如果启动失败并提示 `ports are not available`，优先检查宿主机是否仍有本地 Spring Boot 服务或旧 Compose 前端容器占用 `8000`、`8101`、`8102`、`8103`、`8104`、`8088`。
