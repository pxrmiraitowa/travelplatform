# 微服务改造工作进度与规划

## 1. 文档目的

本文用于统一记录旅游平台从单体应用拆分为微服务架构的当前进度、已完成内容、待完成任务和后续开发顺序。此前按角色和成员拆分编写的协作文档已合并为本文，后续微服务改造统一以本文作为进度说明和开发规划依据。

当前微服务改造目标是：在不破坏原有核心业务演示能力的前提下，将后端逐步拆分为用户服务、产品服务、订单服务、内容行程服务和公共库，并为后续容器化、流水线和网关集成预留稳定结构。

## 2. 当前微服务结构

微服务工程位于 `travel-platform-microservices` 目录下，采用 Maven 多模块结构。

| 模块 | 端口 | 定位 | 当前状态 |
| --- | --- | --- | --- |
| common-lib | 无独立端口 | 公共响应、异常、分页对象、通用常量 | 已创建 |
| user-service | 8101 | 用户注册、登录、JWT、个人资料、用户基础信息 | 已完成第一阶段迁移 |
| product-service | 8102 | 航班、火车、酒店、跟团游、价格比对 | 已完成主要查询接口迁移 |
| order-service | 8103 | 订单创建、支付模拟、订单状态、订单查询 | 已创建骨架，待迁移 |
| content-trip-service | 8104 | 游记、图片上传、行程规划、价格提醒、评价 | 已完成主要内容接口迁移 |

## 4. 当前接口契约

### 4.1 统一响应

所有服务继续使用 `Result<T>` 作为统一响应结构。

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {}
}
```

分页结果统一使用 `PageResult<T>`。

### 4.2 当前登录用户

当前 content-trip-service 已通过 `CurrentUserProvider` 读取：

```http
X-User-Id: 1
```

后续加入 gateway 后，建议由 gateway 完成 JWT 校验，并向下游服务透传 `X-User-Id`。这样 content-trip-service 和 order-service 不需要重复解析 Token。

### 4.3 用户基础信息

user-service 已提供内部批量查询接口：

```http
GET /api/internal/users/basic?ids=1,2,3
```

后续 content-trip-service 中游记、评价展示作者昵称和头像时，应逐步替换为调用该接口。

### 4.4 商品快照

后续 product-service 需要补充商品快照接口，用于 order-service 创建订单、content-trip-service 创建价格提醒时获取商品名称、价格和可用状态。

建议接口：

```http
GET /api/internal/products/snapshot?productType=HOTEL&productId=1
```

建议返回字段：

| 字段 | 说明 |
| --- | --- |
| productType | 商品类型，支持 `FLIGHT`、`TRAIN`、`HOTEL`、`TOUR` |
| productId | 商品 ID |
| productName | 商品展示名称 |
| currentPrice | 当前价格 |
| available | 是否可购买或可预订 |
| stockSummary | 库存、余量、座位等展示信息 |
| coverImage | 商品封面 |

### 4.5 订单评价上下文

后续 order-service 需要给 content-trip-service 提供订单评价上下文，避免评价服务继续直接读取订单表。

建议接口：

```http
GET /api/internal/orders/{orderId}/review-context?userId=1
GET /api/internal/orders/reviewable?userId=1&pageNum=1&pageSize=10
```

评价规则建议分工：

| 规则 | 负责服务 |
| --- | --- |
| 订单是否存在 | order-service |
| 订单是否属于当前用户 | order-service |
| 订单是否已完成 | order-service |
| 订单是否已经评价 | content-trip-service |
| 评价内容是否合法 | content-trip-service |

## 5. 后续开发规划

### 5.1 下一步：order-service

下一阶段建议优先迁移 order-service。原因是评价、支付模拟、订单详情和完整业务闭环都依赖订单服务。

优先完成接口：

| 优先级 | 功能 | 接口 |
| --- | --- | --- |
| P0 | 创建订单 | `POST /api/orders` |
| P0 | 我的订单列表 | `GET /api/orders` |
| P0 | 订单详情 | `GET /api/orders/{id}` |
| P0 | 模拟支付 | `POST /api/orders/{id}/pay` |
| P0 | 取消订单 | `POST /api/orders/{id}/cancel` |
| P1 | 演示用完成订单 | `POST /api/orders/{id}/complete` |
| P1 | 订单评价上下文 | `GET /api/internal/orders/{orderId}/review-context` |
| P1 | 可评价订单 | `GET /api/internal/orders/reviewable` |

### 5.2 第二步：补齐 product-service 商品快照

order-service 和 content-trip-service 都需要商品快照，因此在订单服务主流程完成后，应补齐 product-service 内部商品快照接口。

完成后替换：

| 调用方 | 替换内容 |
| --- | --- |
| order-service | 创建订单时不直接读商品表，改为调用商品快照 |
| content-trip-service | 价格提醒不直接读商品表，改为调用商品快照 |

### 5.3 第三步：替换 content-trip-service 临时适配

content-trip-service 当前为了演示稳定，保留了部分本地表读取。后续应逐步替换：

| 当前临时逻辑 | 替换目标 |
| --- | --- |
| 本地读取用户表展示昵称头像 | 调用 user-service `/api/internal/users/basic` |
| 本地读取商品表创建价格提醒 | 调用 product-service 商品快照接口 |
| 本地读取订单表判断评价资格 | 调用 order-service 评价上下文接口 |

### 5.4 第四步：gateway

在用户、产品、订单、内容服务都具备基本能力后，再增加 gateway 更稳。gateway 主要负责：

| 能力 | 说明 |
| --- | --- |
| 路由转发 | 将前端 `/api/**` 请求转发到对应服务 |
| 认证校验 | 校验 JWT |
| 用户上下文透传 | 向下游服务传递 `X-User-Id` |
| 跨域处理 | 统一处理前端访问 |

建议路径转发：

| 路径 | 服务 |
| --- | --- |
| `/api/auth/**` | user-service |
| `/api/users/**` | user-service |
| `/api/orders/**` | order-service |
| `/api/public/flights/**` | product-service |
| `/api/public/trains/**` | product-service |
| `/api/public/hotels/**` | product-service |
| `/api/public/tours/**` | product-service |
| `/api/public/price-compare/**` | product-service |
| `/api/public/shares/**` | content-trip-service |
| `/api/public/uploads/**` | content-trip-service |
| `/api/shares/**` | content-trip-service |
| `/api/trip-plans/**` | content-trip-service |
| `/api/price-alerts/**` | content-trip-service |
| `/api/reviews/**` | content-trip-service |

注意：评价相关的 `/api/orders/reviewable` 和 `/api/orders/{id}/review` 如果仍作为前端入口保留，需要在 gateway 中优先转发到 content-trip-service。

### 5.5 第五步：容器化与流水线集成

当微服务结构稳定后，再对接另一远程仓库中的容器化和流水线改造。建议新建集成分支处理，而不是直接在当前开发分支硬合并。

建议集成顺序：

1. 拉取包含 Docker 和 CI 的远程分支。
2. 新建集成分支，例如 `codex/microservices-ci-integration`。
3. 合并微服务改造分支。
4. 合并或 cherry-pick 容器化与流水线提交。
5. 调整 Dockerfile、docker-compose、CI 构建命令，使其适配多模块 Maven。
6. 验证至少 `user-service`、`product-service`、`content-trip-service` 可构建。

## 6. 验收标准

阶段性验收建议按以下标准执行：

| 阶段 | 验收标准 |
| --- | --- |
| user-service | 注册、登录、`/api/users/me`、内部用户基础信息接口可用，模块编译通过 |
| product-service | 产品查询和价格比对接口可用，模块编译通过 |
| content-trip-service | 游记、行程、价格提醒、评价接口可用，模块编译通过 |
| order-service | 下单、查询、支付模拟、完成订单、评价上下文接口可用，模块编译通过 |
| gateway | 前端原有路径可访问对应微服务，登录用户可通过 `X-User-Id` 透传 |
| 容器化 | 多服务可通过 docker-compose 启动基础演示环境 |
| 流水线 | CI 能完成前端构建和微服务后端构建 |

## 7. 当前结论

目前微服务改造已经完成基础框架、公共库、产品服务、内容行程服务和用户服务第一阶段迁移。下一步应优先推进 order-service，打通订单主链路，再回头替换 content-trip-service 中的临时本地读取逻辑。

只要订单服务、商品快照接口和用户上下文透传稳定下来，后续 gateway、容器化和流水线集成就会清晰很多，整体微服务改造也能进入可联调、可演示阶段。
