# 微服务改造工作进度与规划

## 1. 文档目的

本文用于统一记录旅游平台从单体应用拆分为微服务架构的当前进度、已完成内容、待完成任务和后续开发顺序。此前按角色和成员拆分编写的协作文档已合并为本文，后续微服务改造统一以本文作为进度说明和开发规划依据。

当前微服务改造目标是：在不破坏原有核心业务演示能力的前提下，将后端逐步拆分为用户服务、产品服务、订单服务、内容行程服务和公共库，并为后续容器化、流水线和网关集成预留稳定结构。

## 2. 当前微服务结构

微服务工程位于 `travel-platform-microservices` 目录下，采用 Maven 多模块结构。

| 模块 | 端口 | 定位 | 当前状态 |
| --- | --- | --- | --- |
| common-lib | 无独立端口 | 公共响应、异常、分页对象、通用常量 | 已创建 |
| gateway-service | 8000 | API 统一入口、JWT 校验、用户上下文透传、路径转发 | 已创建第一阶段网关 |
| user-service | 8101 | 用户注册、登录、JWT、个人资料、用户基础信息 | 已完成第一阶段迁移 |
| product-service | 8102 | 航班、火车、酒店、跟团游、价格比对、商品快照 | 已完成主要查询接口和内部商品快照 |
| order-service | 8103 | 订单创建、支付模拟、订单状态、订单查询 | 已完成主流程迁移 |
| content-trip-service | 8104 | 游记、图片上传、行程规划、价格提醒、评价 | 已完成主要内容接口迁移和跨服务读取替换 |

## 4. 当前接口契约

### 4.1 统一响应

所有服务继续使用 `Result<T>` 作为统一响应结构。

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {}
}
```

分页结果统一使用 `PageResult<T>`。

### 4.2 当前登录用户

当前 content-trip-service 已通过 `CurrentUserProvider` 读取：

```http
X-User-Id: 1
```

后续加入 gateway 后，建议由 gateway 完成 JWT 校验，并向下游服务透传 `X-User-Id`。这样 content-trip-service 和 order-service 不需要重复解析 Token。

### 4.3 用户基础信息

user-service 已提供内部批量查询接口：

```http
GET /api/internal/users/basic?ids=1,2,3
```

后续 content-trip-service 中游记、评价展示作者昵称和头像时，应逐步替换为调用该接口。

### 4.4 商品快照

product-service 已提供商品快照接口，用于 order-service 创建订单、content-trip-service 创建价格提醒时获取商品名称、价格和可用状态。

当前接口：

```http
GET /api/internal/products/snapshot?productType=HOTEL&productId=1
```

订单场景可传入具体规格：

```http
GET /api/internal/products/snapshot?productType=HOTEL&productId=1&variantId=10
GET /api/internal/products/snapshot?productType=TRAIN&productId=1&variantName=二等座
```

建议返回字段：

| 字段 | 说明 |
| --- | --- |
| productType | 商品类型，支持 `FLIGHT`、`TRAIN`、`HOTEL`、`TOUR` |
| productId | 商品 ID |
| productName | 商品展示名称 |
| variantId | 商品规格 ID，酒店房型场景使用 |
| variantName | 商品规格名称，酒店房型、火车席别场景使用 |
| summary | 商品摘要，用于订单展示 |
| currentPrice | 当前价格 |
| available | 是否可购买或可预订 |
| stock | 当前库存或余量 |
| stockSummary | 库存、余量、座位等展示信息 |
| coverImage | 商品封面 |

### 4.5 订单评价上下文

order-service 已给 content-trip-service 预留订单评价上下文，后续需要将评价服务中的本地订单读取替换为该内部接口。

建议接口：

```http
GET /api/internal/orders/{orderId}/review-context?userId=1
GET /api/internal/orders/reviewable?userId=1&pageNum=1&pageSize=10
```

评价规则建议分工：

| 规则 | 负责服务 |
| --- | --- |
| 订单是否存在 | order-service |
| 订单是否属于当前用户 | order-service |
| 订单是否已完成 | order-service |
| 订单是否已经评价 | content-trip-service |
| 评价内容是否合法 | content-trip-service |

## 5. 后续开发规划

### 5.1 已完成：前端统一接入 gateway

前端已将 Vite 本地代理从单体后端 `8080` 切换到 gateway `8000`，请求工具支持通过 `VITE_API_BASE_URL` 覆盖 API 地址。默认本地开发仍使用 `/api` 路径，由 Vite 转发到 `http://localhost:8000`。后台登录已复用 `/api/auth/login`，后台当前用户信息已复用 `/api/users/me`。

### 5.2 已完成临时演示方案：优惠券链路对齐

当前 order-service 创建订单尚未接收 `couponId`，订单金额按商品快照原价保存。为避免演示时出现前端优惠金额和后端订单金额不一致，已先采用临时演示方案：

| 方案 | 说明 |
| --- | --- |
| 已完成临时演示方案 | 机票、酒店、旅游产品预订页隐藏优惠券选择，订单金额以服务端商品快照为准 |
| 后续完整业务方案 | 在 `OrderCreateRequest` 增加 `couponId`，并由 order-service 调用优惠券能力校验优惠券和计算优惠金额 |

### 5.3 已完成：联调说明和验收脚本

已新增 `docs/微服务网关联调说明.md`，说明服务端口、启动顺序、gateway 路由、烟测脚本和端到端业务验收流程。已新增 `travel-platform-microservices/scripts/start-local-services.ps1` 和 `travel-platform-microservices/scripts/smoke-gateway.ps1`，用于启动本地五个后端服务，并检查 gateway 公开路由、未登录拦截、登录和带 token 用户信息查询。

### 5.4 下一步：容器化与流水线集成

当微服务结构稳定后，再对接另一远程仓库中的容器化和流水线改造。建议新建集成分支处理，而不是直接在当前开发分支硬合并。

建议集成顺序：

1. 拉取包含 Docker 和 CI 的远程分支。
2. 新建集成分支，例如 `codex/microservices-ci-integration`。
3. 合并微服务改造分支。
4. 合并或 cherry-pick 容器化与流水线提交。
5. 调整 Dockerfile、docker-compose、CI 构建命令，使其适配多模块 Maven。
6. 验证至少 `user-service`、`product-service`、`content-trip-service` 可构建。

## 6. 验收标准

阶段性验收建议按以下标准执行：

| 阶段 | 验收标准 |
| --- | --- |
| user-service | 注册、登录、`/api/users/me`、内部用户基础信息接口可用，模块编译通过 |
| product-service | 产品查询和价格比对接口可用，模块编译通过 |
| content-trip-service | 游记、行程、价格提醒、评价接口可用，跨服务读取用户、商品、订单上下文，模块编译通过 |
| order-service | 下单、查询、支付模拟、完成订单、评价上下文接口可用，模块编译通过 |
| gateway | 前端原有路径可访问对应微服务，登录用户可通过 `X-User-Id` 透传，管理路径具备基础角色拦截 |
| 容器化 | 多服务可通过 docker-compose 启动基础演示环境 |
| 流水线 | CI 能完成前端构建和微服务后端构建 |

## 7. 当前结论

目前微服务改造已经完成基础框架、公共库、产品服务、内容行程服务、用户服务、订单服务主流程迁移和第一阶段 gateway。product-service 已提供内部商品快照接口，order-service 已切换为基于该接口创建订单快照，content-trip-service 已将用户、商品、订单三类跨服务读取替换为内部 HTTP 调用。

下一步应优先执行五服务加前端的真实端到端联调，再进入容器化和流水线集成。整体微服务改造已经进入可联调、可演示阶段。
