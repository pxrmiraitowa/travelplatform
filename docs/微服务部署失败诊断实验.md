# 微服务部署失败诊断实验

## 1. 实验目标

证明能够从服务日志、健康检查、就绪状态和版本号中定位一次真实可复现的部署失败，并在诊断后恢复服务。

## 2. 自动演练

在 GitHub Actions 页面手动运行 `Microservices CI/CD - GitHub Actions, GHCR and Kind`，打开 `run_failure_drill`。流水线会：

1. 记录 `gateway-service` 当前镜像。
2. 临时替换为不存在的镜像版本。
3. 等待部署超时并确认出现 `ErrImagePull`、`ImagePullBackOff` 或拉取失败事件。
4. 保存 Deployment 描述、Pod 列表和按时间排序的 Kubernetes 事件。
5. 自动恢复原镜像并等待就绪。

实现脚本为 `scripts/failure-drill.sh`。演练产物随部署证据上传，目录为 `artifacts/failure-drill/`。

## 3. 现场排查顺序

| 检查项 | 观察内容 | 本实验结论 |
| --- | --- | --- |
| 就绪检查 | 新 Pod 是否 Ready，Deployment 是否完成 rollout | 新 Pod 不就绪，rollout 超时 |
| 事件 | Pod 最近事件 | 镜像拉取失败，直接定位错误镜像版本 |
| 服务日志 | 容器日志是否存在启动异常 | 容器未启动时无业务日志，应先处理镜像拉取 |
| 健康检查 | `/api/public/health` | 旧副本仍可用时健康，但不能代表新版本已部署 |
| 版本号 | `/api/public/version` 与 Deployment 镜像标签 | 用于确认恢复后运行的是原版本 |

因此，部署判定不能只看 HTTP 健康接口，必须同时检查 rollout/就绪状态、事件和版本信息。正常流水线通过 `scripts/health-check.sh` 自动检查这几项，并保留诊断日志。
